## 1. 先搞懂：我们到底在做什么

### 1.1 「本地能跑」和「线上能访问」差了十万八千里

在本地，你的电脑上跑着 Docker Desktop，用 `docker compose up -d` 把 MySQL、Redis、后端、前端一起拉起来，浏览器打开 `localhost:8080` 就能看到页面。**这是「开发环境」。**

上线要做的是：把这一整套搬到一台**在互联网上有公网 IP 的机器**上，让**全世界任何人**都能通过一个网址访问它，并且要保证：

- 机器重启后服务能自己起来
- 内存不会突然爆掉把进程杀掉
- 不会有陌生人通过 SSH 猜密码登进来
- 数据库里的数据不会丢
- 网站挂 HTTPS（浏览器显示小锁 🔒），不然会被标记「不安全」

这中间的差距，主要是**五件事**：买机器、加固系统、部署代码、配置域名、建立备份与监控。

### 1.2 这次上线用到的东西一览

| 名称 | 是什么 | 在这次上线里的角色 |
|---|---|---|
| **阿里云 ECS** | 云服务器（远程的一台 Linux 电脑） | 承载整个项目 |
| **Ubuntu 22.04 LTS** | 服务器操作系统 | 跑 Docker 的底座 |
| **SSH** | 远程登录服务器的协议 | 我（和未来的你）怎么操作服务器 |
| **密钥对** | 一对 `.pem` 文件（私钥+公钥） | SSH 登录凭证，比密码安全 |

| **Docker Compose** | 容器编排工具 | 一条命令按配置启动 6 个容器 |
| **nginx** | Web 服务器 / 反向代理 | 对外唯一入口，负责分发请求、压缩、限流、HTTPS |
| **MySQL 8.0** | 关系型数据库 | 存商品、订单、用户 |

## 2. 本地 Docker 跑通（起点）

### 2.1 本地启动

```bash
cd E:/PeakFlow
docker compose up -d --build
```

这会构建镜像并启动容器。启动后用 `docker compose ps` 能看到各服务状态。

### 2.2 本地各服务是什么

| 服务 | 端口（容器内） | 作用 |
|---|---|---|
| `mysql` | 3306 | 数据库，数据存在 Docker Volume 里 |
| `redis` | 6379 | 缓存 |
| `namesrv` | 9876 | RocketMQ 的「通讯录」，告诉客户端 broker 在哪 |
| `broker` | 10911 / 10909 | RocketMQ 本体，存消息、投递消息 |
| `backend1` / `backend2` | 8080 | Spring Boot 后端（本地跑 2 个实例演示负载均衡） |
| `nginx` | 80 | 前端静态资源 + 反代 `/api` 到后端 |

### 2.3 上线前必须做的本地验证：5 层回归测试

这一套是项目自带的，位于 `backend/postman/`。**上线前必须全绿，这是底线。**

```bash
docker compose exec -T -w /workspace/backend/postman tester sh -c '
  python3 seed_base_data.py  --db peakflow_dev --redis-db 0   # ⚠️ 会清库重建
  python3 setup_test_data.py --db peakflow_dev --redis-db 0
  newman run PeakFlow-API.postman_collection.json \
      -e env-test.postman_environment.json --env-var baseUrl=http://nginx/api
  python3 verify_db_redis.py && python3 smoke_test.py
'
docker compose exec -T tester mvn -B -ntp verify
```

实测结果（上线前跑过两次，都全绿）：

| 层 | 结果 |
|---|---|
| 种子 + 夹具 | 10 分类 / 100 商品 / 60 秒杀商品 |
| Newman 接口全量 | **123 请求 / 768 断言 / 0 失败** |
| 落库校验 | **11/11**（资金/退款/秒杀闭环 + 库存一致性 + 一人一单门闩） |
| 端到端冒烟 | **18/18** |
| Maven 单测 | **204 测试 / 0 失败** |

> ⚠️ **一个必须记住的坑**：newman 必须在 `postman/` 目录下跑（或加 `-w /workspace/backend/postman`）。
> 集合里上传用例的 `src` 是相对路径 `fixtures/test-avatar.png`，而 newman 按**当前工作目录**解析它。
> 在 `backend/` 直接跑会导致「请求不带文件 → 后端 MultipartException → 业务码 5000」，
> 2 个上传用例 4 个断言失败。表象很像「上传功能坏了」，实际只是目录不对。

### 2.4 为什么本地绿了还不算完

本地跑通只证明「代码逻辑没问题」。上线还额外要求：

- 生产用的配置（`prod` profile）能正确启动
- 内存上限调好，不会 OOM
- 对外暴露的端口只有必要的
- 密钥全部换成随机值（不能用平时开发那套）

## 3. 上线前必须决策的 6 件事

### 3.1 服务器规格：为什么最终选「2 核 4G」

先看项目实测的内存占用（这是决定规格的唯一依据）：

| 容器 | 实测常驻 |
|---|---|
| backend1（JVM） | 812 MB |
| rmq-broker（JVM） | 712 MB |
| mysql | 427 MB |
| rmq-namesrv（JVM） | 212 MB |
| redis + nginx | 21 MB |
| **合计** | **约 2.2 GB** |

加上系统本身约 0.3 GB ⇒ **至少要 4 GB 内存**。2 GB 会 OOM，或者必须砍掉 RocketMQ。

**另一个关键点是 CPU 类型**（这一点很多人栽跟头）：

| 实例族 | CPU 机制 | 适不适合 7×24 跑 JVM |
|---|---|---|
| **通用算力型 u1 / u2a** | ✅ 100% 基准算力，**无积分、不降频** | ✅ 适合 |
| 经济型 e | ⚠️ 共享型，有基线约束，性能有波动 | ⚠️ 勉强 |
| **轻量应用服务器** | ❌ **突发性能实例（CPU 积分制）**，基线只有 10~20% | ❌ **不适合** |
| t5 / t6 | ❌ 积分制，最差 | ❌ 不适合 |

**积分制的坑**：机器闲时攒「积分」，忙时消耗；积分耗尽后 CPU 被限制在基线水平，页面会突然变卡。
对博客这类白天有流量、晚上没流量的站点无所谓，但**你这种 7×24 常驻 4 个 JVM + 数据库的场景会被反复踩**。

### 3.2 付费类型：包年包月 vs 按量付费

| | 包年包月 | 按量付费 |
|---|---|---|
| 付款 | 先付后用 | 先按小时计费，后付费 |
| 价格 | 便宜（年付省约 50%） | 贵 |
| 灵活性 | 想释放要退订 | 随时释放 |
| **能不能 ICP 备案** | ✅ **可以**（需 ≥3 个月） | ❌ **不可以** |

### 3.3 要不要备案（这是个硬门槛）

中国大陆的服务器，「域名 + 80/443 端口」对外提供服务**必须 ICP 备案**，否则会被运营商拦截。

备案的三个硬条件（阿里云官方）：
1. 服务器在**中国内地**地域
2. 计费方式为**包年包月**，且**购买时长 > 3 个月**
3. 已购买公网带宽

**境外服务器不需要备案**。这次最终选了**美国（弗吉尼亚）**，正是为了绕开这个门槛 —— 代价是国内访问稍慢。

### 3.4 域名后缀怎么选

| 后缀 | 首年 | 续费 | 能备案 | 评价 |
|---|---|---|---|---|
| **`.top`** | 1~19 元 | ~39 元 | ✅ | **推荐** |
| `.cn` | 19~35 元 | ~49 元 | ✅ | 也行 |
| `.xyz` | 1 元 | **88 元** | ✅ | ❌ 续费陷阱 |
| `.me` / `.io` / `.ai` / `.app` / `.dev` | — | — | ❌ | 不在工信部批复名单，**不能备案** |

**买域名时只能选个人认证的阿里云账号**（企业认证账号买不了学生优惠）。

### 3.5 用不用学生算力包

学生专属算力包的形态是「**额度**」而不是「机器」：

| 套餐 | 价格 | 额度 | 有效期 |
|---|---|---|---|
| 练手包 | 19 元 | 150 元 | 1 个月 |
| 毕设包 | 339 元 | 850 元 | 6 个月 |
| 科创包 | 389 元 | 2000 元 | 6 个月 |

**毕设包可以叠加 300 元学生券 ⇒ 实付 39 元拿 850 元额度。**

⚠️ **但算力包只能创建「按量付费」实例 ⇒ 不能备案**。这是必须提前知道的限制。

### 3.6 安全基线：上线前必须做的加固

一台刚买来的云服务器，默认状态是**不适合直接放业务**的：

- 允许 root 用密码 SSH 登录（公网 22 端口每天被扫描器撞密码）
- 没有防火墙
- 没有 swap
- Docker 没装
- 系统日志无限增长，迟早写满磁盘

这些在第 5 节一步步解决。

## 4. 企业规范：哪些文件能进仓库，哪些绝对不能

### 4.1 核心原则

> **代码可以公开，密钥绝对不行。**

代码仓库（尤其是 GitHub 公开仓库）会被全网爬虫扫描。有专门的服务实时监控 GitHub 上的 commit，
一旦发现 AWS/Aliyun 密钥、数据库密码，**几秒内就会有人拿它去挖矿**。

**判断标准只有一条**：这个文件里有没有「**只有你和你服务器知道的东西**」？

### 4.2 文件分类清单

| 文件/目录 | 能进仓库？ | 为什么 |
|---|---|---|
| `backend/src/**` 源码 | ✅ | 代码本身没有秘密 |
| `frontend/src/**` 源码 | ✅ | 同上 |
| `docker-compose.yml` | ✅ | 只引用变量名，不含值 |
| `docker-compose.prod.yml` | ✅ | 同上 |
| `backend/Dockerfile` / `frontend/Dockerfile` | ✅ | 构建步骤 |
| `deploy/nginx/*.conf` | ✅ | 配置 |
| `deploy/scripts/*.sh` | ✅ | 已做成参数化，密钥从 `.env` 读 |
| `deploy/mysql/init/*.sql`（建表/基础数据） | ✅ | 结构定义 |
| **`.env`** | ❌ **绝对不能** | **含 DB_PASSWORD / JWT_SECRET / MOCK_PAY_SECRET** |
| **`.env.example`** | ✅ | **只有键名、值是空的**，是给人抄的模板 |
| **`*.pem` / `*.key` / `*.p12`** | ❌ **绝对不能** | SSH 私钥、证书私钥 |
| `deploy/mysql/init/04-demo-account.sql` | ⚠️ 可以但**仅 dev** | 里面有公开密码的演示账号，**生产禁止加载** |
| `backend/logs/` | ❌ | 运行时产物，可能含用户数据 |
| `backend/target/` | ❌ | 构建产物，会被重新生成 |
| `frontend/dist/`、`node_modules/` | ❌ | 同上 |
| `backups/*.sql.gz` | ❌ | 数据库全量备份，含真实数据 |
| 部署用的 SSH 私钥 | ❌ | 拿到它就等于拿到服务器 |

### 4.3 `.gitignore` 的意义

`.gitignore` 是一个「**黑名单文件**」，写在里面的路径，`git` 会**无视**它们，永远不会被提交。

PeakFlow 的 `.gitignore` 里有关键的几条：

```gitignore
.env                    # 生产密钥
.env.local
.dis_env
*.pem
*.key
backend/logs/
backend/uploads/
backend/target/
frontend/dist/
frontend/node_modules/
backups/
```

**验证方法**（很重要，改完 `.gitignore` 一定验一次）：

```bash
git check-ignore -v .env                    # 应输出 .gitignore:行号:.env
git check-ignore -v backend/postman/newman-report.json
```

### 4.4 实操：怎么判断一个文件有没有密钥

**方法一：按文件类型猜**
- 名字里带 `env`、`secret`、`key`、`pem`、`p12`、`credential` ⇒ **高度怀疑**
- 后缀是 `.sql.gz`（备份）⇒ **怀疑**
- 在 `logs/`、`target/`、`dist/`、`node_modules/` 下 ⇒ **排除**

**方法二：搜关键词（最可靠）**

```bash
# 在仓库里搜有没有硬编码的密码/密钥
grep -rniE "password\s*[:=]\s*['\"][^'\"]{6,}|secret\s*[:=]\s*['\"]|BEGIN.*PRIVATE KEY" \
  --include="*.java" --include="*.yml" --include="*.sh" --include="*.js" .
```

**方法三：看提交前 diff**

```bash
git status          # 看有哪些新文件/改动
git diff --cached   # 提交前看暂存区内容（关键！）
```

### 4.5 这次我们实际是怎么做的

项目设计上已经考虑到了这些：

1. **`.env.example` 进仓库**，里面全是空值或占位符：
   ```
   DB_PASSWORD=
   JWT_SECRET=
   MOCK_PAY_SECRET=
   ```
2. **`.env` 由脚本在服务器上现场生成**，密钥全部随机（`gen-prod-env.sh`）：
   - `DB_PASSWORD`：32 位随机字母数字
   - `JWT_SECRET`：64 位随机
   - `MOCK_PAY_SECRET`：40 位随机
3. **`.env` 权限设成 600**（只有属主能读写），属主是部署账号 `peakflow`
4. **生产库不加载演示账号**：`05-provision-envs.sh` 只把 `01-schema` / `02-base-data` / `03-product-data` 灌进 `peakflow_prod`，**刻意排除含公开密码的 `04-demo-account.sql`**

> ⚠️ **一个必须知道的细节**：生成 `.env` 的脚本里有这么一段提醒：
> **千万不要改 `DB_PASSWORD`** —— MySQL 数据卷里的 root 密码只在【首次初始化】时生效，
> 改了会导致后端连不上库（要改就得连数据卷一起重建）。改时间、改其他变量都随意，就它不能动。

## 5. 服务器初始化：从裸机到能部署（12 步）

这一步由 `deploy/scripts/server-init.sh` 完成，**只需执行一次**（幂等，重复执行只会确认状态）。

### 第 1 步：时区与时间同步

```bash
timedatectl set-timezone Asia/Shanghai
timedatectl set-ntp true
```

**为什么**：应用里大量用 `LocalDateTime.now()`，容器时区固定为 Asia/Shanghai，
宿主机如果是 UTC，日志时间会比业务时间差 8 小时，排查问题时会出现「订单创建时间在未来」这种诡异现象。
时间不同步还会影响 HTTPS 证书校验和 JWT 过期判断。

### 第 2 步：基础软件

```bash
apt-get update
apt-get install -y curl ca-certificates gnupg git unzip ufw fail2ban unattended-upgrades htop jq net-tools
```

### 第 3 步：装 Docker

**为什么用 apt 装而不是官网一键脚本**：apt 装的是发行版维护的包，能随系统一起被自动安全更新打补丁，
升级/卸载路径清晰；一键脚本装完就脱离包管理了。

**daemon.json 三个关键配置**：

```json
{
  "log-driver": "json-file",
  "log-opts": { "max-size": "10m", "max-file": "3" },
  "live-restore": true,
  "registry-mirrors": []
}
```

| 配置 | 为什么 |
|---|---|
| `log-opts` 10m×3 | 不设的话容器日志无限增长，40G 磁盘迟早被写满 |
| `live-restore: true` | Docker 守护进程重启/升级时容器不跟着停，减少停机 |
| `registry-mirrors` | **国内机器必须配**（直连 Docker Hub 基本不通），且**要配多个** —— 单个加速站会 502。**美国机器留空**（直连最快） |

### 第 4 步：创建部署账号（不用 root 日常操作）

```bash
adduser --disabled-password --gecos "" peakflow
usermod -aG sudo,docker peakflow
echo "peakflow ALL=(ALL) NOPASSWD:ALL" > /etc/sudoers.d/90-peakflow
```

**为什么**：
- 日常操作犯错（比如 `rm` 打错路径）时，非 root 账号是第一道保险
- 审计上能分清「是人操作还是系统操作」
- 这个账号加入 `docker` 组 —— 注意**这等于给了它 root 级权限**（能挂载宿主目录），
  所以它是「运维账号」不是「受限账号」，只是比直接用 root 好一点

### 第 5 步：SSH 加固（最关键、最危险的一步）

写入 `/etc/ssh/sshd_config.d/00-peakflow-hardening.conf`：

```
PermitRootLogin prohibit-password      # root 只能密钥登录
PasswordAuthentication no              # 彻底禁止密码登录
KbdInteractiveAuthentication no
PubkeyAuthentication yes
MaxAuthTries 3                         # 每连接最多试 3 次（默认 6）
ClientAliveInterval 300
X11Forwarding no
AllowAgentForwarding no
AllowTcpForwarding no
LogLevel VERBOSE
```

**三个必须理解的细节**：

1. **文件名必须用 `00-` 开头**。Ubuntu 云镜像里有 `/etc/ssh/sshd_config.d/50-cloud-init.conf`，
   它通常写着 `PasswordAuthentication yes`，而 sshd 是「**先读到的值生效**」。
   我们的文件名排在它**前面**才能盖住它。为了双保险，脚本还会把那个文件里相关的行注释掉。

2. **必须 `sshd -t` 校验通过才 reload**。一个语法错误就会让你再也连不上：
   ```bash
   sshd -t || die "sshd 配置校验失败，已放弃 reload"
   systemctl reload ssh
   ```

3. **保底退路**：阿里云控制台的「**VNC 远程连接**」走的是云平台通道，**不经过网络栈**，
   所以即使 SSH 全挂了也能进去修。（但「Workbench」走的是 SSH，会一起失败。）

### 第 6 步：防火墙 ufw

```bash
ufw --force reset
ufw default deny incoming
ufw default allow outgoing
ufw allow 22/tcp comment 'SSH'
ufw allow 80/tcp comment 'HTTP'
ufw allow 443/tcp comment 'HTTPS'
ufw --force enable
```

**顺序不能乱**：先 `allow 22` 再 `enable`，反了会把自己关在门外。

**一个必须知道的真相**：Docker 发布端口是通过 iptables 的 `DOCKER` 链实现的，**它会绕过 ufw 的规则**。
所以「哪些端口真正对公网开放」最终由 `docker-compose` 里的 `ports` 决定。
ufw 的价值在于挡住**非 Docker 的进程**（比如你临时装的软件）意外对外监听。

> ⚠️ **我们踩过的坑（已修）**：脚本如果在 ufw 段被中断，会留下「**已启用 + 但没有放行 22**」的死状态，
> 结果 SSH 从外面完全连不上。而且 **ping 仍然是通的**（ufw 默认放行 ICMP echo），
> 极其容易被误判成「安全组问题」。
> **修法**：启用前先确认 22 规则真的进去了，否则**宁可让防火墙保持关闭**（能进去修）：
> ```bash
> if ufw show added | grep -qE 'allow .*22/tcp'; then ufw --force enable
> else die "ufw 未成功写入 22 规则，已放弃启用（保持关闭，避免锁死）"; fi
> ```

### 第 7 步：fail2ban

```ini
# /etc/fail2ban/jail.d/peakflow.local
[DEFAULT]
bantime  = 1h
findtime = 10m
maxretry = 5
backend  = systemd

[sshd]
enabled  = true
port     = 22
maxretry = 4
```

与 SSH 的 `MaxAuthTries` 是两层：`MaxAuthTries` 管单连接，`fail2ban` 管累计。

### 第 8 步：swap（小机器必做）

```bash
fallocate -l 2G /swapfile
chmod 600 /swapfile
mkswap /swapfile && swapon /swapfile
echo '/swapfile none swap sw 0 0' >> /etc/fstab
```

**为什么**：4G 内存同时跑 MySQL + Redis + RocketMQ + JVM，常态约 2.2~2.5G，
但发版/GC/导入数据时会出现瞬时尖峰。**没有 swap，尖峰的直接后果是 OOM Killer 随机杀进程**
（通常是杀 MySQL，最惨）。有了 swap 只会变慢，不会崩。

配套 `vm.swappiness = 10` —— 尽量别用 swap（毕竟慢），只在真的不够时才用。

### 第 9 步：内核参数

```ini
# /etc/sysctl.d/99-peakflow.conf
vm.overcommit_memory = 1              # Redis 官方要求：允许内存过量分配，否则 fork 持久化可能失败
vm.swappiness = 10
net.core.somaxconn = 2048             # 半连接队列上限
net.ipv4.tcp_max_syn_backlog = 4096
net.ipv4.tcp_fin_timeout = 15
net.ipv4.tcp_tw_reuse = 1
fs.file-max = 1000000                 # 文件句柄上限（容器里跑 JVM + MySQL 都吃这个）
net.core.default_qdisc = fq
net.ipv4.tcp_congestion_control = bbr # BBR 拥塞控制，高丢包链路吞吐更好
```

### 第 10 步：限制系统日志

```ini
# /etc/systemd/journald.conf.d/99-peakflow.conf
[Journal]
SystemMaxUse=200M
SystemMaxFileSize=50M
MaxRetentionSec=2week
```

journald 默认能吃掉磁盘的 10%，40G 盘就是 4G。必须收紧。

### 第 11 步：自动安全更新 + certbot

```bash
# /etc/apt/apt.conf.d/20auto-upgrades
APT::Periodic::Update-Package-Lists "1";
APT::Periodic::Unattended-Upgrade "1";
```

**只自动装【安全补丁】，不自动升级大版本** —— 避免某次自动升级把 MySQL/Docker 的版本换掉导致业务起不来。
配置里 `Unattended-Upgrade::Allowed-Origins` 只勾 `security` 源，且 `Automatic-Reboot "false"`。

### 第 12 步：验证

执行完脚本，终端会打印一份汇总。**你要确认这几项**：

```

root 登录   : 仅密钥

swap        : 2.0Gi
BBR         : bbr
```

## 6. 代码怎么上服务器

### 6.1 三种方式对比

| 方式 | 优点 | 缺点 | 适用 |
|---|---|---|---|
| **`git clone`** | 最规范，改代码只需推仓库再拉 | 服务器要能访问 GitHub（国内常超时）；需要部署密钥 | 长期维护首选 |
| **scp 源码包** | 不依赖外网，几秒传完 | 每次要手动打包上传 | 本次采用 |
| **本地构建传镜像** | 服务器不用装 JDK/Node | 镜像几百 MB，传输慢 | 构建环境特殊时 |

### 6.2 本次的做法

由于构建时服务器访问 GitHub 不稳定，采用「**打源码包 + scp**」：

```bash
# ① 从 Git 导出干净的已跟踪文件（不含未提交的改动、不含忽略文件）
rm -rf /tmp/pfsrc && mkdir -p /tmp/pfsrc
git archive HEAD | tar -x -C /tmp/pfsrc

# ② 叠加生产部署文件
cp -r deploy-staging/. /tmp/pfsrc/

# ③ 移除不需要的
rm -f /tmp/pfsrc/backend/src/main/java/com/zhou/peakflow/config/MqSwitch.java
rm -f /tmp/pfsrc/docker-compose.no-mq.yml

# ④ 打包（只有 1.8M）
tar -czf /tmp/peakflow-src.tar.gz -C /tmp/pfsrc .
```

然后传到服务器解压：

```bash
scp -i ~/.ssh/peakflow_deploy /tmp/peakflow-src.tar.gz peakflow@<IP>:/tmp/
ssh -i ~/.ssh/peakflow_deploy peakflow@<IP> '
  sudo mkdir -p /opt/PeakFlow
  sudo tar -xzf /tmp/peakflow-src.tar.gz -C /opt/PeakFlow
  sudo chown -R peakflow:peakflow /opt/PeakFlow
'
```

> ⚠️ **打源码包时必须重新导出**。我们曾因为 tarball 是几分钟前打的、漏掉了刚修的 gzip 配置，
> 导致线上没生效。**核对手段**：
> ```bash
> tar -xzOf 包文件 ./deploy/nginx/peakflow-prod.conf | grep -c "^gzip"
> ```

```bash

```

参数含义：`<对外访问地址> [NGINX端口] [域名] [MQ开关]`

```bash

```

### 6.4 生产配置和开发配置的 6 处差异

生产用「覆盖文件」`docker-compose.prod.yml`，而不是另写一份完整 compose
（另写一份 = 两份真相，改了基础配置忘记同步就会「本地能跑、线上行为不一样」）。差异：

1. **只跑 1 个后端实例** —— 2C4G 装不下两个 JVM。`backend2` 被划进 `multi-instance` profile
2. **逐服务内存上限 + 容器日志上限** —— 小机器上防 OOM、防日志写满
3. **MySQL / Redis 按小内存调优**
4. **nginx 挂载生产站点配置**，额外发布 443
5. **后端以 prod profile 运行**，用 `JAVA_OPTS` 精确控制 JVM 内存
6. **后端日志目录权限交给部署脚本处理**（容器内是非 root 用户跑）

### 7.4 生产库没有账号 —— 演示账号怎么建

这是**项目的安全设计**：`peakflow_prod` 库**不含任何演示账号**（含公开密码的 `04-demo-account.sql`
只灌 dev 库）。生产建号要走**两步流程，密码全程不进入代码仓库**：

```bash
# 第一步：通过接口注册（密码由应用 BCrypt 加密后落库）
curl -X POST -H 'Content-Type: application/json' \
  -d '{"username":"pfadmin","password":"<你的密码>","email":"pfadmin@x.com","nickname":"超级管理员"}' \
  http://127.0.0.1/api/auth/register

# 第二步：用脚本授权角色（新注册默认是 user 角色）
sed -e "s/^SET @username  = .*/SET @username  = 'pfadmin';/" \
    -e "s/^SET @role_code = .*/SET @role_code = 'admin';/" \
    deploy/mysql/prod/grant-admin-role.sql > /tmp/g.sql

docker exec -i -e MYSQL_PWD="$DBP" peakflow-mysql \
  mysql -uroot --default-character-set=utf8mb4 --database=peakflow_prod < /tmp/g.sql
```

> ⚠️ **坑**：`grant-admin-role.sql` 里有**中文列别名**（`AS 角色编码自检`），
> 而 `docker exec ... mysql` 默认字符集不是 utf8mb4，中文会被解码成乱码导致
> `ERROR 1064` 语法错误。**必须加 `--default-character-set=utf8mb4`**。

可选角色：`user` / `admin` / `product_ops` / `order_service`

## 8. 域名与 HTTPS

### 8.1 域名实名认证（买完必须做）

新注册的域名状态会显示 **`client hold`**（解析被暂停），`nslookup` 返回 NXDOMAIN。
原因是**实名认证还没通过**。流程：

```
控制台 → 域名 → 域名列表 → 点域名 → 实名认证
→ 选择/创建【信息模板】：真实姓名（与身份证一致）、身份证号、邮箱、电话
→ 上传身份证正反面 → 提交 → 等审核（通常 1~3 小时，最长 1 个工作日）
```

**验证是否生效**：
```bash
nslookup -type=NS 你的域名 8.8.8.8
# NXDOMAIN    ⇒ 还没生效
# 返回 hichina.com 的 NS ⇒ 已生效，可以加解析了
```

### 8.2 DNS 解析

```
控制台 → 域名 → 点域名 → 解析设置 → 添加记录
   记录类型   A
   主机记录   @              ← @ 表示域名本身
   解析线路   默认
   记录值     <服务器公网IP>
   TTL        10 分钟
```

### 8.3 签 HTTPS 证书

**两种校验方式**：

| 方式 | 要求 | 适用 |
|---|---|---|
| **HTTP-01** | CA 能访问 `http://域名/.well-known/acme-challenge/xxx` | 服务器 80 端口公网可达（**境外服务器不受备案限制**） |
| **DNS-01** | 在 DNS 加一条 TXT 记录 | 80 端口被占用/被备案拦截时 |

```bash
bash deploy/scripts/issue-cert.sh
```

签发后要配置：

| 项 | 配在哪 |
|---|---|
| 80 → 443 的 **301 跳转** | `templates/peakflow-tls.conf.template` 里的 80 server |
| 证书链（`fullchain`，含中间证书） | 同上，`ssl_certificate` |
| TLS 只留 1.2 / 1.3 + 现代加密套件 | 同上 |
| **5 个安全响应头** | `snippets/peakflow-security-headers.inc` |
| 证书自动续期 | crontab（见 8.5） |

### 8.4 安全响应头（5 个，缺一不可）

| 头 | 挡什么 |
|---|---|
| `X-Content-Type-Options: nosniff` | 禁浏览器"猜"内容类型（防把内容是 HTML 的 `.jpg` 当网页执行 → XSS） |
| `X-Frame-Options: SAMEORIGIN` | 禁别的站点用 iframe 嵌套本站 → 防点击劫持 |
| `Referrer-Policy: strict-origin-when-cross-origin` | 跨站跳转时不把完整 URL（可能含订单号）带给对方 |
| `Permissions-Policy` | 明确关掉定位 / 麦克风 / 摄像头权限 |
| **`Strict-Transport-Security`（HSTS）** | 让浏览器此后一律走 HTTPS，防降级攻击 |

> ⚠️ **两个必须知道的坑**（都真实踩过）：
>
> **① HSTS 不能只写在 443 server 的 server 级。**
> nginx 的 `add_header` 是「**就近覆盖**」语义：location 里只要自己设了任何 `add_header`，
> server 级那几条在该 location 里就**全部失效**。
> 所以 HSTS 必须和其余 4 个头放在**同一个 snippet** 里，随 locations 一起 include，
> 否则会出现「配置文件里明明有 HSTS、`curl -I` 却看不到」的诡异现象。
>
> **② `expires` 也算「设了响应头」。**
> `/assets/`（`expires 1y`）与 `= /index.html`（`expires -1`）这两个 location
> 必须**各自再 `include` 一次**安全头片段，否则那两个 location 的安全头会漏。
> 本项目 `peakflow-locations.inc` 里就是按这个规则写的 —— 改那个文件时要特别小心。

### 8.5 自动续期

Let's Encrypt 证书有效期 **90 天**，必须自动续期（项目已加进 crontab）：

```cron
30 3 * * * cd /opt/PeakFlow && bash deploy/scripts/issue-cert.sh --renew >> /var/log/peakflow-certbot.log 2>&1
```

## 9. 服务器平时是怎么运转的

### 9.1 六个容器各自的角色

```
                    Internet
                       │
                  ┌────▼────┐
                  │  nginx  │  ← 唯一对外入口（80/443）
                  └────┬────┘
        静态资源（前端）│  /api/* 反代
        ┌──────────────┴──────────────┐
        │                             ▼
   前端 dist 文件              ┌──────────────┐
                              │  backend1    │  ← Spring Boot（唯一实例）
                              └──────┬───────┘
                     ┌───────────────┼───────────────┐
                     ▼               ▼               ▼
              ┌──────────┐   ┌──────────┐   ┌──────────────────┐
              │  mysql   │   │  redis   │   │ namesrv + broker │
              │  数据落地 │   │ 库存/缓存 │   │  秒杀异步削峰     │
              └──────────┘   └──────────┘   └──────────────────┘
```

### 9.2 一次请求的完整路径（以秒杀下单为例）

1. 浏览器 → `POST https://peakflow.top/api/seckill/order`
2. nginx 收到：先按 IP 做**限流**（秒杀 5 req/s）；检查安全响应头
3. nginx 反代给 `backend1:8080`
4. backend1 校验 JWT → 查 Redis 库存 → **Redis 预扣减**
5. backend1 往 broker 发一条消息，立即返回「排队中」
6. broker 把消息投给消费者 → 消费者**异步写 MySQL**
7. 前端轮询查询结果 → 拿到订单号

**为什么要这么绕**：秒杀瞬间几千请求，直接打 MySQL 会把它压死。
Redis 预扣减 + MQ 异步落库是标准的「削峰」套路。

### 9.3 资源占用（实测）

| 容器 | 内存占用 / 上限 |
|---|---|
| backend1 | 381 MB / 1.37 GB |
| rmq-broker | 646 MB / 700 MB |
| mysql | 215 MB / 850 MB |
| rmq-namesrv | 166 MB / 320 MB |
| redis | 10 MB / 192 MB |
| nginx | 5 MB / 128 MB |
| **合计** | **约 1.8 GB / 3.6 GB** |

swap 只用了 1 MB ⇒ **内存宽裕**。

### 9.4 日志在哪

| 日志 | 位置 |
|---|---|
| backend1 应用日志 | `/opt/PeakFlow/backend/logs/backend1/`（bind mount，宿主机可见） |
| nginx 访问/错误日志 | `docker logs peakflow-nginx` |
| 容器标准输出 | `docker logs <容器名>` |
| 备份任务输出 | `/var/log/peakflow-backup.log` |
| 证书续期输出 | `/var/log/peakflow-certbot.log` |
| 系统日志 | `journalctl -u docker --since "1 hour ago"` |

### 10.4 常见故障排查手册（都是真踩过的）

| 现象 | 第一反应查什么 | 真实原因（这次遇到的） |
|---|---|---|
| **502 Bad Gateway** | 先看后端日志，再看 nginx | ① nginx 陈旧 DNS（重建后端后没重启 nginx）② **沙箱/本机有 HTTP 代理，代理编造的 502**（`curl -v` 看 `Uses proxy env variable`） |

| **数据库连不上** | `docker logs peakflow-mysql` | 改过 `.env` 里的 `DB_PASSWORD`（数据卷里的密码是首次初始化时固化的） |
| **磁盘满** | `df -h`、`docker system df` | 容器日志没设上限 / journald 没限制 |
| **容器反复重启** | `docker compose logs --tail=100 <svc>` | 内存上限太小触发 OOM / 配置写错 |

```bash
# ── 第 3 步：确认没把密钥提交进去 ──────────────
git status
git diff --cached            # 提交前一定要看这个

# ── 第 4 步：提交并推送 ──────────────────────
git add <具体文件>            # 别用 git add . ，容易误加
git commit -m "feat: xxx"
git push origin main

# ── 第 5 步：把新代码送到服务器 ────────────────
#  方式 A（推荐，需服务器能访问 GitHub）
ssh peakflow@<IP> 'cd /opt/PeakFlow && git pull origin main'

#  方式 B（本次用的：打源码包 + scp）
rm -rf /tmp/pfsrc && mkdir -p /tmp/pfsrc
git archive HEAD | tar -x -C /tmp/pfsrc
cp -r deploy-staging/. /tmp/pfsrc/          # 生产文件叠加（如果用了这套）
tar -czf /tmp/peakflow-src.tar.gz -C /tmp/pfsrc .
scp -i ~/.ssh/peakflow_deploy /tmp/peakflow-src.tar.gz peakflow@<IP>:/tmp/
ssh -i ~/.ssh/peakflow_deploy peakflow@<IP> '
  cd /opt/PeakFlow
  tar -xzf /tmp/peakflow-src.tar.gz -C /opt/PeakFlow
  chown -R peakflow:peakflow /opt/PeakFlow'

# ── 第 6 步：重新构建并启动 ───────────────────
ssh peakflow@<IP> 'cd /opt/PeakFlow && bash deploy/scripts/deploy.sh'

# ── 第 7 步：验收 ────────────────────────────
curl -s -o /dev/null -w "%{http_code}\n" http://<IP>/healthz
```

### 11.2 只改了前端（最快，约 1 分钟）

```bash
# 本地
git archive HEAD frontend | tar -x -C /tmp/fe
scp -r -i ~/.ssh/peakflow_deploy /tmp/fe/frontend peakflow@<IP>:/tmp/
# 服务器
ssh peakflow@<IP> '
  cd /opt/PeakFlow
  rsync -a /tmp/frontend/ frontend/
  docker compose -f docker-compose.yml -f docker-compose.prod.yml build nginx
  docker compose -f docker-compose.yml -f docker-compose.prod.yml up -d nginx'
```

> ⚠️ **改了 `frontend/nginx/default.conf` 或 `deploy/nginx/*.conf` 不用重新 build**，
> 因为配置是 bind mount 的，直接 reload 就行：
> ```bash
> docker exec peakflow-nginx nginx -t && docker exec peakflow-nginx nginx -s reload
> ```

### 11.3 只改了后端

```bash
ssh peakflow@<IP> '
  cd /opt/PeakFlow
  # 只重建后端镜像 + 重启后端
  docker compose -f docker-compose.yml -f docker-compose.prod.yml build backend1
  docker compose -f docker-compose.yml -f docker-compose.prod.yml up -d backend1
  # ⚠️⚠️ 后端重建后【必须重启 nginx】，否则 nginx 还连旧 IP，表现为 502 且后端无日志
  docker compose -f docker-compose.yml -f docker-compose.prod.yml restart nginx'
```

### 11.4 改了数据库结构

**这是最需要谨慎的情况。** 生产库有真实数据，不能像开发库那样 DROP 重建。

1. 先写一个 `ALTER TABLE` 迁移脚本（**不要**用 `DROP TABLE`）
2. **先备份**：`bash deploy/scripts/backup.sh`
3. 在**预发环境或本地**用生产数据的副本测一遍
4. 生产执行：`docker exec -i -e MYSQL_PWD=xxx peakflow-mysql mysql -uroot --default-character-set=utf8mb4 peakflow_prod < migrate.sql`
5. 再发后端代码
6. 验证

⚠️ 注意：`deploy/mysql/init/01-schema.sql` 每张表前都有 `DROP TABLE IF EXISTS`，
**它只在数据卷首次初始化时执行**。所以「改 schema 文件」对已有生产库**完全无效**，必须用 ALTER。

### 11.5 回滚

```bash
# 代码回滚
git revert <坏提交的hash>     # 生成一个反向提交，安全
git push origin main
# 然后走 11.1 的 5~7 步重新部署

# 或者用 git reset（本地回退，需强推，谨慎）
git reset --hard <好提交的hash>
git push --force-with-lease origin main

# 数据回滚（最后手段）
ls -lh /opt/PeakFlow/backups/
gunzip -c backups/peakflow_prod-20261017-031059.sql.gz | \
  docker exec -i -e MYSQL_PWD=xxx peakflow-mysql mysql -uroot peakflow_prod
```

### 11.6 改代码时的常见错误

| 错误 | 后果 | 正确做法 |
|---|---|---|
| `docker compose exec` 里改代码 | 改的是容器内副本，容器一重建就没了 | 改宿主机/本地的源码文件 |
| `docker compose exec tester mvn package` | **不会更新运行中的镜像 jar** | 必须 `docker compose build` |
| 改了代码没 `build` 就 `up -d` | 跑的还是旧代码 | 用 `deploy.sh`（内含 build） |
| 重建后端后没重启 nginx | 502，且后端日志无记录 | `restart nginx` |
| `git add .` | 可能把 `.env`、`.pem` 提交上去 | 明确 `git add <文件>` |
| 直接改生产 `.env` 里的 `DB_PASSWORD` | 后端连不上库 | 这个值**永远不要改** |

## 12. 这次踩过的 21 个坑（全清单）

按踩到顺序，全部真实发生：

| # | 现象 | 根因 | 解法 |
|---|---|---|---|
| 1 | newman 上传用例 4 个断言失败、业务码 5000 | newman 按**当前工作目录**解析 `src` 相对路径 | 必须在 `postman/` 目录下跑，或加 `-w /workspace/backend/postman` |
| 2 | 文档说的种子数据数量和实际不符 | 脚本后来追加了 50 条秒杀商品，文档没跟 | 以脚本运行时输出为准，订正 4 处文档 |
| 3 | Docker 拉 `redis` 返回 **502 Bad Gateway** | 单个国内镜像加速站会 502 | daemon.json 配**多个**加速站，自动回退 |
| 4 | 一键脚本静默死掉、一个字都不输出 | `set -o pipefail` + `tr </dev/urandom \| head -c 32` ⇒ **head 关闭管道，tr 收 SIGPIPE 退出 141** ⇒ `set -e` 中断 | `... \| head -c "$n" \|\| true` + **显式校验长度** |
| 5 | 生产 nginx 完全没 gzip，首屏要等 5~8 秒 | 写生产配置时漏了；**nginx 默认只压缩 `text/html`**，JS/CSS/JSON 全不压 | 显式配 `gzip_types`，实测 1.25MB→404KB |
| 6 | `grant-admin-role.sql` 报 `ERROR 1064` | 脚本里有**中文列别名**，mysql 客户端默认字符集不是 utf8mb4 ⇒ 乱码 | 加 `--default-character-set=utf8mb4` |
| 7 | 加固脚本中断后 SSH 全断，但 **ping 还通**（误导性极强） | ufw 留下「已启用 + 无放行 22」状态；**ufw 默认放行 ICMP echo** | 启用前校验 22 规则，否则放弃启用；用控制台 **VNC**（不走网络栈）抢救 |
| 8 | 安全组规则明明允许 22 却不生效 | **阿里云安全组按地域隔离** —— 规则加到了北京那个默认安全组，美国实例用的是另一个 | 先在地域切换器切到目标地域，再确认实例实际所属的安全组 ID |
| 9 | 排查半天"服务器故障"，其实服务器好的 | **本机到目标 IP 的网络路径不通**（纯网络问题） | **用第二台机器（已有 SSH 权限的）去测目标端口**，别只信自己这台 |
| 10 | 用跳板机报 `stdio forwarding failed` | **自己写的加固脚本设了 `AllowTcpForwarding no`**，把跳板需要的端口转发禁了 | 临时改 `yes`；这也说明加固要按用途调整 |
| 11 | 线上 nginx 没 gzip，但文件里明明有 | 源码包是**几分钟前**打的，漏了刚修的配置 | 打包前重新 `git archive`，并**核对包内内容** |
| 12 | VNC 里 `Ctrl+V` 粘贴报 `: command not found` | **VNC 终端不支持粘贴** | 长命令走控制台「发送命令/云助手」，或手打极短命令 |
| 13 | 证书明明签好了，`deploy.sh` 却判定「没有证书」⇒ **443 一直不通** | 证书存在性判断用了裸 `[ -f ]`，而 `/etc/letsencrypt/live` 与 `/archive` 默认是 `drwx------ root root`，非 root 的部署账号读不到 | 回退到 `sudo -n test -f`（只需判存在；证书内容由 Docker 守护进程以 root 挂进容器）。**⚠️ 不要**用 `chmod 755 /etc/letsencrypt/live` 这个常见偏方 —— 那等于把 `privkey.pem` 暴露给本机所有用户 |
| 14 | nginx 报 `unhealthy`、`deploy.sh` 判定「有服务未就绪，部署中断」，**但站点其实完全正常** | 镜像里的 healthcheck 是 `wget http://127.0.0.1/healthz`；启用 HTTPS 后 80 端口一律 **301 跳转**，wget 默认**跟随跳转** ⇒ 容器内要解析域名走公网 hairpin ⇒ 失败 | 在 HTTPS 覆盖层里重定义 healthcheck，接受 `200\|301\|302` —— 健康检查要回答的是「nginx 还活着吗」，不是「业务接口通不通」 |
| 15 | HSTS 在配置里写了，响应里却**没有**这个头 | 写在 TLS 模板的 **server 级**，而 `peakflow-locations.inc` 里凡是自己设过 `add_header` 的 location（`/assets/`、`= /index.html`）会丢弃 server 级**全部** `add_header` | 把 HSTS 挪进 `snippets/peakflow-security-headers.inc`，与其余 4 个头**同层级**。（在 `http://` 上多带该头无害：RFC 6797 §7.2 规定浏览器只在 HTTPS 上才认） |
| 16 | 往 `.env.example` 加键，**加了重复键** —— 好在自查时发现 | 该文件已有 `NGINX_PORT` / `PUBLIC_BASE_URL`，我又在新增段落里定义了一遍。`.env` 同名键以**最后一条**为准 ⇒ 会造成「改了上面、生效的是下面」的隐性错位 | **加键前先查重**：`grep -oE '^[A-Z_][A-Z0-9_]*=' .env.example \| sort \| uniq -d` |
| 17 | 生产环境收银台点「确认支付」报**「网络异常 / JSON 格式不支持」**，本地却完全正常 | 收银台页面 `mock-pay-cashier.html` 把收款接口写死为**根相对路径** `fetch('/mock-pay/pay')`。生产收银台经 nginx 以 `/api/mock-pay/cashier` 暴露，该 fetch 实际打到 `https://域名/mock-pay/pay` ⇒ nginx 无此 location ⇒ **405 HTML** ⇒ 页面 `r.json()` 解析失败。本地默认 `cashier-url=http://127.0.0.1:8080/mock-pay/cashier`（根路径直挂）恰好能通，所以 newman/集成测试（服务端直调、不经过浏览器 fetch）全绿也发现不了 | 接口地址改为**文档相对路径** `fetch('pay')`，由浏览器按页面自身 URL 解析 —— 生产 `/api/mock-pay/pay`、本地 `/mock-pay/pay` 都正确，**零配置两环境通吃**；同时给响应处理加 `r.ok` 检查与「非 JSON 响应」的可读提示。教训：**后端静态页面里写接口路径，一律用文档相对路径或完整 URL，别用根相对路径** —— 页面挂载前缀在不同环境是会变的 |
| 18 | 手动重建 nginx 后**全站 443 拒绝连接**（`ERR_TUNNEL_CONNECTION_FAILED` / connection refused），约 2 分钟事故 | 重建时只写了 `-f docker-compose.yml -f docker-compose.prod.yml`，**漏掉 `-f docker-compose.https.yml`** ⇒ 重建出的容器丢了 443 端口映射和证书挂载。容器 healthcheck 走的是 80 的 `/healthz`，照样显示 healthy ⇒ **「healthy」不代表对外服务完整** | 重建生产 nginx **永远用 `bash deploy/scripts/deploy.sh`**（它会检测到证书后自动带上 https 覆盖层），不要手拼短栈 compose 命令；恢复后必须从**外网视角**验证 443（`curl -sI https://域名`），容器内 healthy 不算数 |
| 19 | 秒杀商品**有库存却提示已售罄**、库存显示 0，但点抢购又能成功 | 后端 `Product` 有两个独立库存字段：`stock`（普通库存，秒杀商品恒为 0）与 `seckillStock`（真实可抢量）。详情页的展示/售罄提示/进度条全读 `stock`，只有抢购校验读 `seckillStock` ⇒ 同一页面自相矛盾。**接口契约本身没问题，是前端用错了字段** | 统一按 `isSeckill` 取正确口径（`availableStock` / `stockLabel`），展示与校验同源；秒杀数量上限固定 1（后端唯一索引限购）。已在 `docs/API.md` 明确两字段语义 |
| 20 | 用户取消秒杀订单后，**再抢同一商品被拦 24 小时**（「您已参与过该秒杀活动」） | DB 限购位 `seckill_slot` 在取消后按设计释放（status∈(4,5) ⇒ 生成列变 NULL），但 Redis 购买权门闩 `seckill:order:success:{userId}:{productId}`（24h TTL）只在**失败路径**释放，取消路径漏了 ⇒ Redis 与 DB 判重不一致 | `OrderServiceImpl#rollbackStock` 的秒杀分支在回补 DB + Redis 库存的同时调用 `releasePurchaseGate(userId, productId)`；已补单测守卫。**注意历史残留**：修复前产生的门闩不会自动清除，需手工 `DEL`（本次清了一条） |
| 21 | 登录页协议勾选框**完全勾不上**，导致无法登录 | 把《用户协议》《隐私政策》两个 `<a>` 放进了 `el-checkbox` 的 label 内，并用 `@click.prevent.stop` 阻止冒泡 ⇒ 点击事件被拦截，复选框的 label 关联勾选失效（自引入回归，生产实测才发现） | 协议文案与链接**移出** `el-checkbox`（checkbox 独立、文字用 `span` 承载），链接只用 `@click.prevent`；补「真实点击 input 必须勾上」的回归测试 |

## 附：这份手册里最该记住的 5 句话

1. **密钥永远不进仓库**，`.env` / `.pem` / 备份 一律 `.gitignore`。
2. **改密码要小心**：`.env` 里的 `DB_PASSWORD` 只在数据卷首次初始化时生效，改了就断连。
3. **重建后端必须重启 nginx**，否则 502 且后端日志里看不到请求。
4. **判定「服务器故障」前，先用第二台机器验证** —— 很多时候是自己这台机器的网络问题。
5. **上线前本地 5 层回归必须全绿**（123 请求 / 768 断言 / 11 落库 / 18 冒烟 / 204 单测）。
