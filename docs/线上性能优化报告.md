# PeakFlow 线上访问缓慢 · 排查与修复报告

- **报告时间**：2026-10-18（北京时间）
- **环境**：`https://peakflow.top`（阿里云美国弗吉尼亚 ECS，2 核 4G）
- **触发来源**：用户反馈「别的设备第一次登录，商品列表要一两分钟才出来，头像加载极慢，很多地方都慢」
- **一句话结论**：**不是 Redis / 后端的问题**（用户判断正确）。慢在跨国链路传输量上，
  另有一个被掩盖的**功能缺陷**——上传的图片从外网根本打不开。

---

## 一、先分层定位：慢在哪一层

排查的第一步不是改代码，是把「一次首屏」拆成可独立测量的层。
所有测量都用 `curl --noproxy '*'`（本机有代理，会把外网结果污染成假 502）。

### 1.1 后端在服务器内部只要几毫秒

| 测量点 | 结果 |
|---|---|
| nginx 内 `curl 127.0.0.1/api/product/page` | **0.28 ms** |
| 直连 `backend1:8080/product/page`（跳过 nginx） | **6.0 ms** |
| Redis 命中率 | `keyspace_hits 14644 / misses 12070`（约 55%） |
| Redis 内存 | `1.88 MB / 128 MB` |

**结论**：后端与 Redis 完全不是瓶颈。0.28ms 的接口从国内访问要 1.8s，
差 6000 倍 —— 全部是跨国网络与传输量。

### 1.2 从国内访问的真实分层耗时

| 层 | 改造前 |
|---|---|
| HTML（875 字节） | TTFB **2.1 ~ 2.7 s** |
| 主 JS（未压缩 1.25MB） | **8.8 s** |
| 主 JS（gzip 404KB） | **6.3 s** |
| CSS（gzip 51KB） | **3.9 s** |
| API `product/page` | **1.8 ~ 2.0 s** |
| 商品图（unsplash 单张） | 1.2 ~ 2.8 s × 10+ 张 |

换算下来有效吞吐约 **60 KB/s**。这就是「一两分钟」的来源：
1.25MB 的 JS + 十几张 30~70KB 的图 + 多次 API 往返，串起来就是分钟级。

### 1.3 顺手排除了一个误判

一开始 `curl` 显示 `HTTP/1.1`，我误以为 HTTP/2 没开。用 ALPN 探测后发现：

```
openssl s_client -alpn h2 -connect peakflow.top:443 → ALPN protocol: h2
```

**HTTP/2 一直是开的**，是本机 `curl 7.81` 编译时没带 HTTP/2 支持
（`--http2: the installed libcurl version doesn't support this`）。
又是一次「观测工具本身不可信」。

## 二、五个根因（按影响从大到小）

### 根因 1（最严重，且是**功能缺陷**）：上传的图片从外网根本打不开

后端未配 OSS 时降级把文件写到容器内 `./uploads`，返回
`https://域名/uploads/<uuid>.png`。但 **nginx 里没有 `/uploads/` 的 location**，
请求落到最后一条 SPA 回退规则：

```nginx
location / { try_files $uri $uri/ /index.html; }
```

静态目录没有这个文件 → 回退成 `index.html` → 浏览器拿到
`200 + text/html + 875 字节` → `<img>` 解码失败 → **图片永远显示不出来**。

实测对照（同一个 1.33MB 头像文件）：

| 访问路径 | 结果 |
|---|---|
| 直连 `backend1:8080/uploads/xxx.png` | `200  image/png  1330273 bytes` |
| 经 nginx `https://域名/uploads/xxx.png` | `200  text/html       875 bytes` |

**所以用户说的「头像加载非常缓慢」，实际是「头像一直加载不出来」。**
这是本轮最重要的发现 —— 它不是性能问题，是 bug。

### 根因 2：上传的图片原样落盘，单个头像 1.33MB

`OssUploadServiceImpl` 只校验「≤5MB + 扩展名」，然后把原始字节直接写入，
没有任何缩放或重编码。线上 `/app/uploads/` 的实际文件：

```
1330273 / 826464 / 484789 / 388047 / 385964 / 324554 字节（合计 3.6MB）
```

全是用户手机原图。5MB 的上限对头像场景形同虚设。
在 60KB/s 链路上，**一个 1.33MB 头像就要 20 秒以上**，而页面上有多个头像展示位。

### 根因 3：前端主 chunk 单文件 1.22MB

`main.js` 里两处「全量引入」：

```js
import ElementPlus from 'element-plus'                       // 全量组件
import * as ElementPlusIconsVue from '@element-plus/icons-vue'  // 293 个图标全注册
```

图标库共 **293 个导出**，项目实际只用到 **28 个**。其余 265 个图标连同
element-plus 全部组件都进了首屏包 —— 单文件 1.22MB，gzip 404KB，
在 60KB/s 下就是 6~9 秒。而且**每次发版业务代码一变，这个巨大的包缓存全失效**。

### 根因 4：商品图统一 `w=800`，且全部来自境外 unsplash

商品列表卡片的实际展示宽度只有 200~260px（2x 屏按 400 已足够），
却统一请求 800px 的图。10+ 张图 × 30~70KB 全部来自 `images.unsplash.com`，
每张都要重新做 DNS + TCP + TLS（跨国 3 个 RTT ≈ 1 秒）。

首屏轮播图更严重：硬编码 `w=800&h=400&q=80`，是首屏视觉面积最大的一张。

### 根因 5：静态资源缓存策略不完整

- `/assets/` 有 `max-age=1y` 但没有 `immutable` → 每次访问仍有 304 条件请求往返（每个 ≈330ms）
- `/uploads/` 完全没有缓存头（因为压根没有 location）

---

### 根因 6（部署后才发现）：压缩代码从未被调用

第一轮"修复"上线后，重新上传一张 1192KB 的图，线上文件**仍然是 1192KB**。
查容器内 jar：

```
ImageCompressor.class                     ← 在
OssUploadServiceImpl 引用 ImageCompressor  ← False   ← 问题在这
```

`ImageCompressor` 编译进 jar 了，但上传服务里**根本没调用它**。
原因是 `OssUploadServiceImpl` 的接入改动在某次 `git reset --hard` 中丢失 ——
该类是已跟踪文件，reset 把修改一起回滚；而新建的 `ImageCompressor.java`
作为未跟踪文件反而幸存。于是形成「类在、单测全绿、线上不生效」的状态。

**这也是为什么必须补一条"从上传入口进、抓真正写给 OSS 的字节流"的测试**：
只测 `ImageCompressor` 本身发现不了这个缺口（它自测是通的）。

### 根因 7（部署后才发现）：图片 URL 多了一段 `/api`

`docker-compose.yml` 里：

```yaml
APP_UPLOAD_PUBLIC_BASE_URL: ${PUBLIC_BASE_URL}/api
```

`/api` 是给**接口请求**用的 nginx 前缀，图片不是接口。后果：
- 图片 URL 变成 `https://域名/api/uploads/<uuid>.png`
- 请求落到 `location /api/`（带限流、`no-cache`），
  **不会命中专门为图片写的 `location /uploads/`（30 天缓存）**

修复后 URL 是 `https://域名/uploads/<uuid>.png`，正确命中图片专用 location。
历史数据里已存的 `/api/uploads/...` 通过新增兼容 location 继续可用，
并且缓存策略从 `no-cache` 升级为 30 天。

---

### 根因 8（第二轮体检发现）：头像压缩走错了链路

第一轮"修完头像压缩"后，用**全新设备**（清空 82 个临时浏览器 profile 后冷启动）
在真实 UI 上上传一张 1200×1200 的图，结果服务器落地的是**原图 1603KB / 760px**。

追踪发现图片上传有**两个完全独立的入口**：

```
前端 User.uploadAvatar()  →  POST /user/avatar  →  UserServiceImpl#changAvatar  ← 没改
前端（后台商品图）        →  POST /upload/image →  OssUploadServiceImpl#uploadImage ← 只改了这个
```

`changAvatar` 当时仍是「把原始 InputStream 直接交给 aliOssUtil」——零缩放、零重编码。
所以商品图压缩生效、单测也全绿，但**用户头像照旧原样落盘**。

修复后实测：**3.88MB（1200×1200）→ 51KB（400×400），省 98.7%**，
日志明确记录 `头像处理：原始 4068357 bytes → 上传 52221 bytes`。

> **教训**：同一能力有多个入口时必须逐个确认接入。
> 验证方式不是读代码猜，而是**抓真正写给存储的字节**比较体积 ——
> 这也是 `UserServiceImplAvatarTest` 的做法。

### 根因 9（同为第二轮）：2MB 上限会把手机原图直接拒掉

前端校验 2MB / `application.yml` max-file-size 2MB / `MAX_AVATAR_SIZE` 2MB，
而服务端本来就会压到 400px。**手机原图普遍 3~8MB** ⇒ 大量真实用户在
「选择文件」那一刻就被拒绝，而他只是想换个头像。

三处同步放宽到 5MB，并把拒绝提示从「不能超过 2MB」改成
「不能超过 5MB，建议先用手机截图或压缩后再上传」——**说清怎么办**。

---

### 根因 10（第三轮，用户直觉触发）：112 张展示图没有一张在自己的服务器上

用户说「我记得我的图片都是存在我的服务器上的」。查库后发现并非如此：

| 来源 | 数量 | 实际位置 |
|---|---|---|
| 商品图 | 100（94 张去重） | `images.unsplash.com` 境外 CDN |
| 分类图标 | 10 | `images.unsplash.com` 境外 CDN |
| 前端轮播（硬编码在 Home.vue） | 2 | `images.unsplash.com` 境外 CDN |
| 商品图（脏数据） | 15 | `https://域名/favicon.ico` —— 根本不是商品图 |
| 用户上传 | 2 | 本机 uploads ✅ |

前几轮做的 `resolveImage` 只是把境外图的 `w=` 参数调小，
**根子上的跨域握手与无缓存问题一点没解决**。这一轮把它们全部下载到本机。

做法与结果：

· 94 张去重后逐张下载 → 生成 400/800/1000 三档（分级质量 q70/q82/q78）
· 原图合计 **28.8MB → 800 档 6.1MB**（省 79%）
· 123 条图片引用逐条 curl 校验：**125/125 全部 HTTP 200**
· 数据库 115 商品 + 10 分类改为本机地址，**0 条仍指向 unsplash**
· 15 条 favicon 脏数据换成统一占位图
· 轮播图按 1000×400 居中裁剪（固定高容器里不能只等比缩放，会被拉变形）

### 根因 11（同一轮）：`loading="lazy"` 在慢网下并不生效

给 32 张图片都加了 `loading="lazy"`，实测仍然全部请求。
排查后确认容器已有 `padding-top:100%` 占位（不是布局问题），
而是 **Chrome 在慢速网络下会把 lazy 的预加载阈值自动扩大到约 3000px**。

改法不是"跟浏览器对着干"，而是**明确告诉它谁更重要**：
轮播 + 秒杀前 6 个 + 网格前 8 个用 `fetchpriority="high"` 并 `eager`，
其余保持 lazy。目的从"减少总字节"转为"让用户最先看到的那几张先到"。

## 五、过程中自己踩的坑（如实记录）

### 5.1 存量压缩脚本第一版把头像全部搞坏了

初版脚本把「无透明 PNG 转 JPEG」并**改了扩展名**（`.png` → `.jpg`）。
但数据库里存的是 `.../<uuid>.png`，文件变成 `<uuid>.jpg` ⇒ **原 URL 全部 404**。
同时脚本以 root 运行，写出文件属主变 root，而后端容器以 UID 1001 运行 ⇒ 可能读不了。

**已从备份完整还原（6/6 文件 HTTP 200 校验通过）**，并把两条铁律写进脚本：
① 保持原文件名（含扩展名）；② 保持原 uid/gid。

### 5.2 `git reset --hard` 丢了一次前端改动

为撤销一个误提交执行了 `git reset --hard HEAD~1`，它把**未提交的工作区修改一起丢弃**。
新建的未跟踪文件（icons.js 等）幸免，已修改的已跟踪文件（main.js、vite.config.js、
9 个视图）全部回滚。

后果：那次提交只包含 4 个新文件，**接入改动全缺**。部署后 `docker compose build nginx`
全程 CACHED（源码确实没变），线上仍是旧的 1.22MB 单文件 —— 即优化完全没生效。
是「镜像构建时间还是 12 小时前」这个细节暴露了它。

修复：重新应用 11 个文件并单独提交。教训：reset 前先 `git stash`。

### 5.3 回归出现 9 项红，全是脚本缺陷

| 假红 | 真因 |
|---|---|
| 下单 `orderId=None` | 脚本用时间戳当数量：先超库存（113），改后又撞业务上限 `MAX_CART_ITEM_QUANTITY=10` |
| 秒杀 16 并发全部被拦 | 上一轮留下的「待付款秒杀订单」正确占用限购名额；而清理逻辑按 `isSeckill` 过滤，**订单 VO 里只有 `orderType`** ⇒ 恒为 None，静默失效 |
| 购物车数量 3 而非 2 | 购物车存在 Redis（30 天），上一轮残留累积 |
| 手机端缺「库存/加入购物车」 | UI 回归等待 1200ms 不够（现在要下 4 个拆分包），手动打开页面完全正常 |

全部修复后：**API 65/65 · UI 30/30 · 联调 19/19 全绿**。

### 5.4 又一次「观测工具骗了我」

本机 `curl` 显示 HTTP/1.1 → 误判 HTTP/2 未开。实际是 curl 自身未编译 h2 支持，
ALPN 探测证明服务端一直是 h2。**测量结论之前，先确认测量工具本身的能力。**

## 六、接口契约 / 兼容性 / 回滚

| 项 | 结论 |
|---|---|
| 后端 HTTP 接口 | **路径、入参、响应结构全部未变** |
| 上传接口行为 | 返回值仍是图片 URL 字符串；只是文件尺寸变小（压缩后扩展名可能 png→jpg，但**URL 由前端拿到后保存**，不影响存量数据） |
| 老版本前端 | **完全兼容**（未改任何请求/响应格式） |
| 数据库 | **无任何变更**（没有加字段、没有改表结构、没有改存量 URL） |
| Redis | 无结构调整 |
| 回滚 | 代码：`git revert` 对应提交；静态资源：`bash tools/rollback_prod.sh <commit>`；图片：`cp <dir>-orig/* <dir>/`（原图都在） |

## 八、还能继续优化的（本次未做，供后续决策）

1. **商品图走服务端代理 + 磁盘缓存**：现在图片仍从 `images.unsplash.com` 跨域拉取。
   由 nginx 反代并缓存到本地后，可加 1 年 immutable，二次访问零成本。
   本次未做是因为要新增 `proxy_cache_path` 与 `resolver`（http 级改动），
   深夜变更风险偏大，且当前 4.5s 已可用。
2. **首页首屏商品数量**：首页一次渲染 60+ 商品卡片，首屏实际可见约 20 张。
   改为「首屏 12 个 + 滚动加载」可进一步减少首屏图片请求。
3. **element-plus 真正按需引入**：目前只是拆包，组件仍是全量。
   用 `unplugin-vue-components` 可把 vendor-element 从 792KB 降到约 300KB。
   需要加构建依赖并回归全部页面，风险中等。
4. **考虑国内 CDN 或香港节点**：跨国 330ms RTT 是物理限制，
   静态资源走 CDN 可从根上消除。
5. **Brotli 压缩**：当前镜像的 nginx 没编译 brotli 模块，只能 gzip。
   gzip 已省 68%，brotli 还能再省 15~20%。

## 十、三条最该记住的

1. **「慢」和「坏」要分开判断。** 用户说头像加载慢，实际是头像从来没加载成功过
   （返回的是 HTML）。如果只按「性能」去优化，永远修不好。
   **先验证资源到底有没有拿到，再谈快慢。**
2. **跨国链路上，字节数就是秒数。** 60KB/s 意味着 1MB ≈ 17 秒。
   所以「减少传输量」（压缩图片、按需取尺寸、拆包久缓存）的收益远大于
   「优化服务端计算」—— 而后端本来就只有 0.28ms。
3. **`git reset --hard` 会连未提交的修改一起吃掉。** 两次踩到（一次丢 nginx 改动，
   一次丢前端接入改动），第二次的后果是「优化代码在仓库里、但没接进去、线上没生效」，
   只有靠「镜像构建时间还是 12 小时前」这种细节才能发现。reset 前请 `git stash`。
