## 二、排查方法：先分层，再改代码

用户主观感受是「慢」，但「慢」可能来自几十个环节。第一步不是改代码，而是**把一次首屏拆成可独立测量的层**。

### 2.1 第一步就排除了后端

| 测量点 | 结果 |
|---|---|
| nginx 容器内 `curl 127.0.0.1/api/product/page` | **0.28 ms** |
| 直连 `backend1:8080/product/page`（跳过 nginx） | **6.0 ms** |
| Redis 命中率 | `hits 14644 / misses 12070`（约 55%） |
| Redis 内存 | `1.88 MB / 128 MB` |

**结论：后端与 Redis 完全不是瓶颈。** 同一个接口 0.28ms，从国内访问要 1.8 秒 ——
差 6000 倍，全部是跨国网络与传输量。

这也印证了用户的判断「应该不是 Redis 的问题」。

### 2.2 再从国内实测每一层

| 层 | 改造前 |
|---|---|
| HTML（875 字节） | TTFB **2.1 ~ 2.7 s** |
| 主 JS（未压缩 1.25MB） | **8.8 s** |
| 主 JS（gzip 404KB） | **6.3 s** |
| CSS（gzip 51KB） | **3.9 s** |
| API `product/page` | **1.8 ~ 2.0 s** |
| 商品图（单张，境外） | 1.2 ~ 2.8 s × 10+ 张 |

换算下来有效吞吐约 **60 KB/s**（1 MB ≈ 17 秒）。
这就是「一两分钟」的来源：大 JS + 十几张图 + 多次 API 往返串起来。

### 2.3 一个重要的方法论教训

一开始 `curl` 显示 `HTTP/1.1`，我误判「HTTP/2 没开」。用 ALPN 探测才发现：

```
openssl s_client -alpn h2 -connect peakflow.top:443
→ ALPN protocol: h2
```

**HTTP/2 一直是开的**，是本机 `curl 7.81` 编译时没带 HTTP/2 支持
（`--http2: the installed libcurl version doesn't support this`）。

> **教训**：下结论前先确认测量工具本身的能力。
> 之后所有外网测量都加了 `--noproxy '*'`（本机有代理，会把结果污染成假 502）。

## 四、逐个问题

### 问题 1：上传的图片从外网根本打不开（功能缺陷，不是性能问题）

**现象**：用户说「头像加载非常缓慢」。但实际测下来，头像**从来没有加载成功过**。

**排查**：拿同一个文件（1.33MB 的头像）分别从两条路径访问：

| 访问路径 | 结果 |
|---|---|
| 直连 `backend1:8080/uploads/xxx.png` | `200  image/png  1330273 bytes` ✅ |
| 经 nginx `https://域名/uploads/xxx.png` | `200  text/html  875 bytes` ❌ |

**根因**：后端未配 OSS 时降级把文件写到容器内 `./uploads`，返回
`https://域名/uploads/<uuid>.png`。但 **nginx 里没有 `/uploads/` 的 location**，
请求落到最后一条 SPA 回退规则：

```nginx
location / { try_files $uri $uri/ /index.html; }
```

nginx 静态目录里没有这个文件 ⇒ 回退成 `index.html`
⇒ 浏览器拿到 `200 + text/html + 875 字节` ⇒ `<img>` 解码失败 ⇒ 图片永远显示不出来。

**修法**：新增 `location ^~ /uploads/`：

```nginx
location ^~ /uploads/ {
    include     /etc/nginx/snippets/peakflow-security-headers.inc;
    expires     30d;
    access_log  off;
    limit_except GET { deny all; }          # 只允许读
    proxy_pass  http://peakflow_backend/uploads/;
}
```

- 转发给后端而不是让 nginx 直接读：文件在 backend 容器的 named volume 里，nginx 没挂这个卷
- `expires 30d`：文件名是 UUID、内容永不变化 ⇒ 可长缓存
- `limit_except GET { deny all; }`：防止借这个前缀做写操作

**验证**：同一文件现在是 `200 image/png 1330273 bytes`，`Cache-Control: max-age=2592000`。

### 问题 2：上传的图片原样落盘，单个头像 1.33MB

**现象**：线上 `/app/uploads/` 里的实际文件：
`1330273 / 826464 / 484789 / 388047 / 385964 / 324554 字节`，全是用户手机原图。

**根因**：上传接口只校验「≤5MB + 扩展名」，然后把**原始字节直接写入**，没有缩放、没有重编码。
5MB 的上限对头像场景形同虚设。在 60KB/s 链路上，**一个 1.33MB 头像要传 20 秒以上**。

**修法**：新增 `ImageCompressor`（**纯 JDK ImageIO，不引入任何第三方依赖**）：

- 按最长边缩放到 400px（头像展示位 80px，2x 屏 400 已足够）
- 不带透明 → JPEG q0.82 progressive；带透明 → PNG（保 alpha，转 JPEG 会变黑底）
- **只缩不放**：原图小于目标尺寸时保持原尺寸，避免放大模糊 + 体积反增
- 压缩后反而变大 → 保留原图
- webp/gif 原样返回（ImageIO 不支持 webp；GIF 缩放会丢动画）
- **任何异常都回落原图** —— 压缩是优化，不能让上传失败

**验证**：单测与真实日志
`1600x1600 → 400x400：613773 → 44948 bytes（省 93%）`

### 问题 3：前端主 JS 单文件 1.22MB

**根因**：`main.js` 里两处「全量引入」：

```js
import ElementPlus from 'element-plus'                          // 全量组件
import * as ElementPlusIconsVue from '@element-plus/icons-vue'  // 293 个图标全注册
```

图标库共 **293 个导出**，项目实际只用到 **28 个**。其余 265 个图标连同
element-plus 全部组件都进了首屏包。而且**每次发版业务代码一变，这个巨大的包缓存全失效**。

**修法**：

1. `src/icons.js`：图标按需注册，28 个显式名单（由脚本扫描 `src/` 全量后与图标库导出取交集得出，不是手抄）
2. `vite.config.js`：`manualChunks` 拆成 `vendor-vue` / `vendor-element` / `vendor` / `index`
3. 加一个**覆盖率守卫测试**：源码里用到的每个图标必须在注册名单里
   （漏注册只会静默不渲染，编译/类型/普通单测都发现不了）

**验证**：

| 产物 | 改造前 | 改造后 |
|---|---|---|
| 主 index.js | **1222 KB**（单文件） | **14 KB** |
| vendor-element | — | 792 KB（gzip 249KB，**可跨版本长期缓存**） |
| vendor（axios 等） | — | 173 KB（gzip 62KB） |
| vendor-vue | — | 109 KB（gzip 42KB） |
| gzip 合计 | 404 KB | 357 KB |

关键收益不是省了 47KB，而是**发版时用户只需重新下载 5~14KB 的业务代码**。

### 问题 4：商品图统一 `w=800` 且全部来自境外

**根因**：列表卡片实际展示宽度只有 200~260px（2x 屏按 400 已足够），却统一请求 800px。
10+ 张图 × 30~70KB 全部来自 `images.unsplash.com`，每张都要重新做 DNS + TCP + TLS
（跨国 3 个 RTT ≈ 1 秒）。首屏轮播图更严重：硬编码 `w=800&h=400&q=80`。

**修法**（第一轮，不完全）：
新增 `src/utils/image.js` 的 `resolveImage(url, size)`，按场景取尺寸
（thumb 400 / mini 200 / large 800 / banner 1000），q 降到 65 + `auto=format`，
非首屏加 `loading="lazy"`。只对 unsplash 生效，OSS/本地地址原样返回。

> ⚠️ 这个修法只是「把境外图的参数调小」，**没有解决跨域握手与无缓存**。
> 真正的解法见问题 10。

### 问题 5：静态资源缓存策略不完整

**根因**：

- `/assets/` 有 `max-age=1y` 但没有 `immutable` → 每次访问仍有 304 条件请求往返（每个 ≈330ms）
- `/uploads/` 完全没有缓存头（因为压根没有 location，见问题 1）

**修法**：

```nginx
location /assets/ {
    add_header  Cache-Control "public, max-age=31536000, immutable";
}
```

⚠️ 注意：**不能同时用 `expires 1y`**，两者会重复下发 `Cache-Control`，不同浏览器取值不一致。

### 问题 6：压缩代码编译进 jar，但从未被调用（功能缺陷）

**现象**：第一轮「修完上传压缩」并部署后，重新上传一张 1192KB 的图，
线上文件**仍然是 1192KB**。

**排查**：把容器里的 jar 拷出来，用 Python zipfile 反查：

```
ImageCompressor.class                     ← 在
OssUploadServiceImpl 引用 ImageCompressor  ← False   ← 问题在这
```

**根因**：`ImageCompressor` 编译进 jar 了，但上传服务里**根本没调用它**。
原因是 `OssUploadServiceImpl` 的接入改动在某次 `git reset --hard` 中丢失 ——
该类是已跟踪文件，reset 把修改一起回滚；而新建的 `ImageCompressor.java`
作为未跟踪文件反而幸存。于是形成「类在、单测全绿、线上不生效」。

**修法**：

1. 重新接入
2. 新增 `OssUploadServiceImplTest`（5 用例），**从上传入口进、抓真正写给 OSS 的字节流**
   断言体积确实变小

> 只测 `ImageCompressor` 本身发现不了这个缺口 —— 它自测是通的。
> 必须测「入口 → 落盘字节」这条完整链路。

### 问题 7：图片 URL 多了一段 `/api`

**根因**：`docker-compose.yml` 里

```yaml
APP_UPLOAD_PUBLIC_BASE_URL: ${PUBLIC_BASE_URL}/api
```

`/api` 是给**接口请求**用的 nginx 前缀，图片不是接口。后果：

- 图片 URL 变成 `https://域名/api/uploads/<uuid>.png`
- 请求落到 `location /api/`（带限流、`no-cache`），**不会命中专门为图片写的 `location /uploads/`**（30 天缓存）

**修法**：去掉 `/api`。同时为历史数据（库里已存的 `/api/uploads/...`）新增兼容 location：

```nginx
location ^~ /api/uploads/ {
    expires     30d;
    limit_except GET { deny all; }
    proxy_pass  http://peakflow_backend/uploads/;   # 剥掉 /api
}
```

这样老 URL 不仅继续可用，还从 `no-cache` 升级为 30 天缓存。

### 问题 8：头像上传走的是另一条链路，压缩完全没生效（功能缺陷）

**现象**：用**全新设备**在真实 UI 上传一张 1200×1200 的图，服务器落地的是
**原图 1603KB / 760px**（前端 `naturalWidth` 也是 760，说明没缩放）。

**根因**：图片上传有**两个完全独立的入口**：

```
前端 User.uploadAvatar()  →  POST /user/avatar  →  UserServiceImpl#changAvatar  ← 没改
前端（后台商品图）        →  POST /upload/image →  OssUploadServiceImpl#uploadImage ← 只改了这个
```

`changAvatar` 当时仍是「把原始 InputStream 直接交给 aliOssUtil」——零缩放、零重编码。
所以商品图压缩生效、单测全绿，但**用户头像照旧原样落盘**。

**修法**：

1. `changAvatar` 接入 `ImageCompressor`（同一套：最长边 400px）
2. 压缩后扩展名跟随实际格式（PNG→JPEG 时文件名必须变 `.jpg`，
   否则 nginx 会按 `.png` 返回错误的 Content-Type）
3. `ImageIO.read` 的 IOException 显式捕获，给出可读提示而不是 500
4. 新增 `UserServiceImplAvatarTest`（6 用例）

**验证**：实测 **3.88MB(1200px) → 51KB(400px)，省 98.7%**，日志：
`头像处理：原始 4068357 bytes → 上传 52221 bytes，changed=true，尺寸=400x400`

### 问题 9：2MB 上限把手机原图直接拒掉（体验缺陷）

**根因**：三处限制都是 2MB（前端校验 / `application.yml` max-file-size / Java 常量），
而服务端本来就会压到 400px。**手机原图普遍 3~8MB** ⇒ 大量真实用户在
「选择文件」那一刻就被拒绝，而他只是想换个头像。

**修法**：三处同步 2MB → 5MB，并把提示从「不能超过 2MB」改成
「不能超过 5MB，**建议先用手机截图或压缩后再上传**」—— 说清怎么办。

> 三处必须同时改，否则前端放行了后端仍拒、或提示与实际行为不一致。

### 问题 10：112 张展示图，一张都不在自己的服务器上

**起因**：用户说「我记得我的图片都是存在我的服务器上的」。查库后发现**并非如此**：

| 来源 | 数量 | 实际位置 |
|---|---|---|
| 商品图 | 100（94 张去重） | `images.unsplash.com` 境外 CDN |
| 分类图标 | 10 | `images.unsplash.com` 境外 CDN |
| 前端轮播（硬编码在 Home.vue） | 2 | `images.unsplash.com` 境外 CDN |
| 商品图（脏数据） | 15 | `https://域名/favicon.ico` —— 根本不是商品图 |
| 用户上传 | 2 | 本机 uploads ✅ |

前几轮做的 `resolveImage` 只是把境外图的 `w=` 参数调小，
**根子上的跨域握手与无缓存一点没解决**。

**修法**：新增 `tools/localize_images.py`，四种模式：

| 模式 | 作用 |
|---|---|
| `--download` | 拉库里的境外图 → 下载 → 生成 400/800/1000 三档 → 生成 UPDATE SQL（改库前逐条校验文件存在） |
| `--repack` | 改了 400 档质量后，从已有 -800 重压（不必重下 95 张原图） |
| `--banners` | 轮播按 1000×400 居中裁剪（固定高容器不能只等比缩放，会被拉变形） |
| `--verify` | 逐条 curl 校验库里 URL 是否可访问 |

**分级质量**（实测后定，不是拍脑袋）：

| 档位 | 用途 | 质量 |
|---|---|---|
| 400 | 列表卡片（展示 200~260px） | q70 |
| 800 | 详情页主图 | q82 |
| 1000 | 轮播（1000×400 裁剪） | q78 |

**前端配套**：`resolveImage()` 扩展「本机图床」分支 —— 按场景把 `-800` 换成 `-400`。
`pickLocalTier()` 保证**只返回盘上真实存在的档位**（400/800/1000），
否则就是 404 破图；并特意不让 800 降到 400（详情页会发虚）。

**结果**：

- 原图合计 **28.8MB → 800 档 6.1MB**（省 79%）；生成 287 个文件
- **125 条引用逐条 curl 校验：125/125 全部 HTTP 200**，0 缺失
- 数据库：**118 商品 + 10 分类全部本机，unsplash 归零**
- 15 条 favicon 脏数据换成统一占位图
- 首屏图片 720KB → **558KB**；**二次访问 load 0.3s**（图片只传 10KB）

**附带发现**：`loading="lazy"` 在慢网下并不生效 —— Chrome 会把预加载阈值
自动扩大到约 3000px，32 张图仍然全部请求。容器已有 `padding-top:100%` 占位，
所以不是布局问题。改法不是跟浏览器对着干，而是用 `fetchpriority="high"`
明确告诉它谁更重要（轮播 + 秒杀前 6 + 网格前 8）。

### 问题 11：回归脚本「新增商品」不可逆，污染生产库 16 条（测试缺陷）

**现象**：线上商品库里有 16 条 `回归临时商品<时间戳>`，其中 **11 条是上架状态**，
排在商品列表第 5~6 页 —— **用户往后翻就能看到**。

**根因**（两个接口事实，之前都没注意）：

① `POST /product/add` 返回 **void**，`data` 里没有新商品 id。
   脚本写的是 `new_pid = r.get('data')`，永远是 None
   ⇒ `if new_pid:` 整段（修改 + 删除）被**静默跳过**
   ⇒ 商品创建后从未被删掉，但断言只检查「新增成功」，所以一直是绿的。

② `addProduct` 内部强制 `setStatus(ON_SHELF)`，**不管 DTO 传什么**；
   而 `deleteProduct` 明确拒绝删除上架商品（"商品已上架，请先下架再删除"）
   ⇒ 即使拿到 id，直接调用删除也会失败。

**修法**：D1 段改为完整闭环

1. 创建
2. **用 `keyword` 按名称把商品查回来拿 id**（名称有唯一约束，能精确定位）
3. 修改
4. **先下架**（status=0）—— 删除的前置条件
5. 删除
6. **删完再查一次，断言确实没有残留**

新增 5 个断言，回归项数 65 → 70。连续跑两次，第二次结束时库里残留 = 0。

**清理已累积的脏数据**：新增 `tools/clean_test_products.py`，
走**正常业务接口**（下架 → 删除）而不是 `DELETE FROM` ——
直接删库会绕过「在途订单 / 退款占用」校验，可能留下脏引用。

结果：11 条上架残留已删除；另外 5 条是早已软删除（`deleted=1`，业务不可见）。
复查 `name LIKE '回归临时商品%' AND deleted = 0` → **0 条**，商品总数 101 条干净。

> **教训**：「可逆测试」不能只看断言绿不绿，要**验证副作用真的消失了**。
> 第 6 步自检就是为了这个。

## 六、我自己踩的坑（如实记录）

### 坑 1：`git reset --hard` 三次吃掉未提交修改

| 次数 | 丢了什么 | 后果 |
|---|---|---|
| 1 | nginx 配置改动 | 配置文件回滚，重新应用 |
| 2 | 前端接入改动（main.js / vite.config / 9 个视图） | 提交里只有新增文件、没有接入 ⇒ 部署后 `docker build` 全 CACHED、线上仍是旧版 |
| 3 | 后端压缩接入（`OssUploadServiceImpl`） | **`ImageCompressor` 类在 jar 里但从未被调用**，线上头像仍 1.33MB |

**为什么难发现**：`reset --hard` 会丢弃未提交修改，但**未跟踪的新文件不会消失**。
于是形成「新类在、调用没接」的半成品状态 —— 编译通过、单测全绿、只有线上行为不对。
第 2 次是「镜像构建时间还是 12 小时前」这个细节暴露的。

**规矩**：reset 前先 `git stash`；改完立刻 `git add`。

### 坑 2：存量压缩脚本第一版把头像全搞成 404

初版把「无透明 PNG 转 JPEG」并**改了扩展名**（`.png` → `.jpg`），
但数据库里存的是 `.../<uuid>.png` ⇒ **原 URL 全部 404**。
同时脚本以 root 运行，写出文件属主变 root，而后端容器以 UID 1001 运行 ⇒ 读不了。

**已从备份完整还原**（6/6 文件 HTTP 200 校验通过），并把两条铁律写进脚本：
① 保持原文件名（含扩展名）；② 保持原属主。

### 坑 3：回归出现 9 项红，全是脚本缺陷

| 假红 | 真因 |
|---|---|
| 下单 `orderId=None` | 脚本用时间戳当数量：先超库存（113），改后又撞业务上限 `MAX_CART_ITEM_QUANTITY=10` |
| 秒杀 16 并发全被拦 | 上一轮留下的待付款秒杀订单正确占用限购名额；而清理逻辑按 `isSeckill` 过滤，**订单 VO 里只有 `orderType`** ⇒ 恒为 None 静默失效 |
| 购物车数量 3 而非 2 | 购物车在 Redis（30 天），上一轮残留累积 |
| 手机端缺「库存/加入购物车」 | UI 回归等待 1200ms 不够，手动打开完全正常 |

### 坑 4：两个浏览器测试并行跑，出现 6 项成片假红

`fresh_device_check.py` 与 `ui_regression.py` 共用同一个 agent-browser daemon，
并行会**互相抢页面控制权**。串行后同样代码 28/28、30/30 全过。

**规矩**：浏览器类测试必须串行。

### 坑 5：`js()` 解析不了数字，误报 64 处「组件缺失」

检查脚本的 `js()` 只解析被 `JSON.stringify` 的返回值。
`document.querySelectorAll(sel).length` 直接返回数字 ⇒ 匹配不到 ⇒ 判成 0
⇒ 第一次跑报「组件缺失」7 项（实际全在）。加 `js_num()` 后恢复。

### 坑 6：Element Plus 的 `nth-of-type` 选不到第 2 个输入框

每个 input 各自嵌在自己的 `.el-input__inner` 里，都是「父级的第一个 input」。
`input:nth-of-type(2)` 匹配不到 ⇒ 注册表单 6 个框只填上 2 个。
改用 JS 直接赋值 + 派发 `input`/`change` 事件。

### 坑 7：登录页两个 tab 的表单同时存在于 DOM

注册表单虽然 `display:none`，但元素还在。
`placeholder*='用户名'` 会命中隐藏的注册框 ⇒ 登录填了个看不见的输入框、登录失败。
必须用精确等值或结构定位。

### 坑 8：`#tab-register button` 是 tab 头，不是提交按钮

点了只切页签，不提交表单。实际提交按钮是 pane 内的 `button.btn-submit`。

### 坑 9：agent-browser 的 daemon 空闲退出，登录态丢失

daemon 空闲会退出，下次调用换新临时 profile ⇒ localStorage 清空。
表现是「登录成功 → 跳页 → 突然跳回 /login」。
**所有依赖登录态的操作必须写在同一条命令里**。

### 坑 10：临时 profile 无限堆积

每次启动在 `%TEMP%\agent-browser-chrome-<uuid>` 建临时 profile、**从不回收**。
本次清出 **82 个 / 909MB**。

## 九、遗留事项与建议

### 9.1 已知的可优化点（本次未做）

1. **商品 1000 档占用 9.4MB 磁盘但几乎不被请求**
   本地化时给每张商品图都生成了 1000 档，实际只有 2 张轮播用得上。
   不影响流量（没人请求），只是磁盘占用。可后续清理。

2. **`element-plus` 仍是全量引入**
   目前只做了拆包（792KB），用 `unplugin-vue-components` 可降到约 300KB。
   需要加构建依赖并回归全部页面，风险中等。

3. **Brotli 压缩**
   当前镜像的 nginx 没编译 brotli 模块，只能 gzip。brotli 还能再省 15~20%。

4. **国内 CDN 或香港节点**
   跨国 330ms RTT 是物理限制。图片已本地化，但 HTML/JS 仍从美国出。
   上 CDN 可从根上消除这部分延迟。

5. **首页首屏商品数量**
   当前首页渲染 20 个商品卡片，首屏可见约 12 个。改为分屏加载可再省约 130KB。

### 9.2 三条最该记住的

1. **「慢」和「坏」要分开判断。**
   用户说头像加载慢，实际是头像从来没加载成功过（返回 HTML）。
   如果只按「性能」去优化，永远修不好。**先验证资源到底有没有拿到，再谈快慢。**

2. **跨国链路上，字节数就是秒数。**
   60KB/s 意味着 1MB ≈ 17 秒。所以「减少传输量」（压图、按需取尺寸、拆包久缓存）
   的收益远大于「优化服务端计算」—— 而后端本来就只有 0.28ms。

3. **「改了一个地方 + 单测全绿」不等于功能生效。**
   两个上传入口只改一个、压缩类在 jar 里但没被调用、回归创建商品却没删 ——
   这三次都是「代码看起来对、断言也是绿、但线上行为不对」。
   验证方式必须是**端到端抓真实产物**：抓写给 OSS 的字节、查生产库的实际记录、
   对比镜像构建时间。
